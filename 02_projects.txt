PROJECT 1: AI BUSINESS INTELLIGENCE ASSISTANT
Live App: https://ai-bi-assistant.streamlit.app
GitHub: https://github.com/rithujaa/ai-bi-assistant
Built: July 2026 (built and deployed in one afternoon)

What It Does:
An AI-powered business intelligence assistant that lets anyone upload a CSV, Excel, or PDF file and ask questions about their data in plain English. No SQL or coding knowledge required. Think of it as having a data analyst available 24/7 that anyone in a company can use.

Why It Was Built:
Built to learn RAG, LangChain, vector databases, and what it actually takes to ship a real AI application end to end. Not built to compete with ChatGPT — built to demonstrate the ability to design and deploy production AI applications from scratch.

Two Completely Different AI Architectures Under The Hood:

Architecture 1 — For CSV and Excel files (Code Generation + Execution):
When a user uploads a CSV or Excel file and asks a question, GPT-4o doesn't search through text. Instead:
1. The app sends GPT-4o a description of the dataframe (column names, data types, sample rows)
2. GPT-4o writes real pandas Python code to answer the question
3. The code is executed against the actual dataset using Python's exec() function
4. The result is a precisely computed answer, not a guess
5. GPT-4o then explains the result in plain English for non-technical users
This means answers are mathematically exact — not hallucinated text responses.

Architecture 2 — For PDFs (RAG Pipeline):
When a user uploads a PDF:
1. Text is extracted from every page using PyPDF
2. Text is split into chunks of ~1000 characters with 100-character overlap using LangChain's RecursiveCharacterTextSplitter
3. Each chunk is converted into a 1,536-dimensional vector embedding using OpenAI's text-embedding-ada-002 model
4. Embeddings are stored in ChromaDB (an in-memory vector database using EphemeralClient)
5. When a question is asked, it's also embedded and compared against all stored chunk embeddings using cosine similarity
6. The 5 most semantically relevant chunks are retrieved
7. Those chunks + the question are sent to GPT-4o which generates a contextual answer

Key Features:
- Automatic interactive chart generation using Plotly (GPT-4o decides what chart type is appropriate for each question)
- Data quality report on upload (flags missing values, duplicate rows, constant columns)
- One-click executive summary generation (GPT-4o analyzes the full dataset and writes a professional summary)
- Suggested questions generated by GPT-4o based on the actual columns and data in the uploaded file
- Chat history with follow-up question memory (last 3 exchanges used as context)
- Self-healing code execution — if GPT-4o uses a Python library that's not installed, the system catches the error, tells GPT-4o which module failed, and asks it to rewrite the code without that module
- Export conversation as a downloadable text file
- Settings toggles in the sidebar for showing/hiding the pandas code and raw computed results
- Sidebar with file upload, how-to-use guide, and settings

- LangChain — text splitting (RecursiveCharacterTextSplitter) and RAG retrieval pipeline
- ChromaDB (EphemeralClient) — in-memory vector database for PDF RAG, resets between sessions to prevent data bleeding

PROJECT 3: REAL-TIME CDC PIPELINE
GitHub: https://github.com/rithujaa/real-time-data-streaming

What It Does:
A production-grade Change Data Capture (CDC) pipeline that streams data from a source system into Snowflake in real time, tracking every change across three data layers — RAW, SCD1 (current state), and SCD2 (full history). This is the kind of infrastructure that powers real-time analytics in production data platforms.

Why CDC Matters:
Change Data Capture is a pattern where every insert, update, and delete in a source system is tracked and propagated to the data warehouse. Without CDC, you either have to reload all data every time (slow) or miss changes between loads. With CDC, your warehouse always reflects the current state of the source system in real time.

Architecture (Step by Step):
1. A Python script generates synthetic events (inserts, updates, deletes) simulating a source system
2. Apache NiFi, running in Docker on AWS EC2, picks up these events and streams them to AWS S3 in real time
3. Snowpipe, a Snowflake feature, continuously monitors the S3 bucket and automatically loads new files into the Snowflake RAW layer within seconds
4. Snowflake Streams detect changes (inserts, updates, deletes) in the RAW table as they arrive
5. Snowflake Tasks are scheduled to check the Stream every minute
6. When new changes are detected, Tasks trigger SQL stored procedures that process the changes into two layers:
   - SCD1 Layer: Uses a MERGE statement to upsert the current state (no history, fastest queries)
   - SCD2 Layer: Closes old records with an end date and inserts new versions (full history, tracks every change)

Key Technical Details:
- SCD1 stored procedure uses Snowflake's MERGE statement to handle inserts and updates in a single operation
- SCD2 stored procedure sets CURRENT_FLAG = FALSE and END_DATE on the old record, then inserts the new version with CURRENT_FLAG = TRUE and a new START_DATE
- Python reconciliation scripts validate that record counts match between RAW, SCD1, and SCD2 layers
- NiFi is containerized with Docker for portability
- Full pipeline documentation maintained for governance and reproducibility

Tech Stack:
- Python (data generation script, reconciliation and validation scripts)
- Apache NiFi (real-time event streaming, containerized in Docker)
- AWS EC2 (hosting the NiFi container)
- AWS S3 (staging area between NiFi and Snowflake)
- Snowflake (data warehouse with RAW, SCD1, SCD2 layers)
- Snowpipe (auto-ingestion from S3 into Snowflake, near real-time)
- Snowflake Streams (CDC tracking — detects inserts, updates, deletes in RAW table)
- Snowflake Tasks (automated scheduling of stored procedure execution)
- SQL stored procedures (MERGE-based SCD1 upserts, SCD2 history tracking with effective dates)
- Docker (NiFi containerization)

What This Project Demonstrates:
- Deep Snowflake knowledge including Streams, Tasks, Snowpipe, and stored procedures
- Understanding of CDC patterns and SCD1/SCD2 dimensional modeling
- Real-time data pipeline architecture using AWS and Snowflake
- Production-grade thinking — reconciliation scripts, documentation, data quality checks

You can view the full code at https://github.com/rithujaa/real-time-data-streaming

PROJECT 4: E-COMMERCE CLOUD DATA PIPELINE
GitHub: https://github.com/rithujaa/ecom-data-pipeline
Stars: 3

What It Does:
An end-to-end cloud data pipeline for an e-commerce dataset built entirely on Azure. Implements the Medallion Architecture (Bronze, Silver, Gold) for progressive data refinement, fully automated with event-based triggers from ingestion through to analytics.

Architecture (Step by Step):
1. Raw CSV files (Users, Sellers, Buyers, Countries datasets) are uploaded to Azure Data Lake Storage Gen2 (ADLS) in landing-zone-1
2. Azure Data Factory (ADF) detects the new file via a storage event trigger, converts the CSV to Parquet format (columnar, more efficient), and stores it in landing-zone-2
3. The Parquet arrival in landing-zone-2 triggers another ADF pipeline that launches an Azure Databricks job automatically
4. The Databricks job runs three PySpark notebooks — Bronze, Silver, Gold — in sequence:
   - Bronze Layer: Ingests Parquet from landing-zone-2, standardizes schema, casts data types, stores as Delta table
   - Silver Layer: Cleans and enriches Bronze data, removes duplicates, applies business logic, stores as Delta table
   - Gold Layer: Joins and aggregates Users, Sellers, Buyers, and Countries into a single unified comprehensive_user_table stored as Delta
5. Gold data is stored in Delta format in ADLS and connected to Azure Synapse Analytics for SQL querying and dashboarding
6. ADF automatically moves processed files from to_processed_user_data/ to processed_user_data/ for tracking

Key Technical Details:
- Event-based triggers automate the entire pipeline — no manual intervention needed
- Users table uses mode("append") for incremental loading of new records
- All layers stored as Delta tables in /mnt/delta/tables/{bronze|silver|gold}/
- Delta Lake provides ACID transactions and time travel capabilities
- SQL (ecom_sql.sql) used for Synapse queries and final consumption

Tech Stack:
- Azure Data Factory (pipeline orchestration with storage event triggers)
- Azure Data Lake Storage Gen2 (landing zones and Delta Lake storage)
- Azure Databricks (PySpark transformation environment)
- Apache Spark / PySpark (data transformation language)
- Delta Lake (Bronze/Silver/Gold layers with ACID transactions)
- Azure Synapse Analytics (SQL querying and dashboarding of Gold data)
- Python (PySpark notebooks: Bronze Layer.ipynb, Silver Layer.ipynb, Gold Layer.ipynb)
- SQL (ecom_sql.sql for Synapse queries)

What This Project Demonstrates:
- End-to-end Azure cloud data engineering
- Medallion Architecture implementation (Bronze/Silver/Gold)
- Event-driven pipeline automation with Azure Data Factory
- PySpark data transformation at scale
- Delta Lake for reliable, ACID-compliant data storage
- Knowledge of the full Azure data stack

You can view the full code at https://github.com/rithujaa/ecom-data-pipeline

PROJECT 5: CROSS-CITY RESTAURANT INSPECTION PIPELINE (DATABRIDGE)
GitHub: https://github.com/rithujaa/DataBridge

What It Does:
A data integration pipeline that unified restaurant health inspection data from three completely incompatible city datasets (NYC, Chicago, and Boston) into a single analytical data warehouse. The core challenge was that each city named their violations completely differently, making direct comparison impossible.

The Problem:
NYC called a violation "temperature control failure." Chicago called the same thing "improper holding temperature." Boston called it "temperature maintenance." Manual mapping of thousands of violation categories across three cities would have taken weeks and been error-prone.

The Solution — Using NLP and AI to Automate Standardization:
Instead of manual mapping, the pipeline used semantic similarity to automatically match violation categories across cities:
1. Each violation category from all three cities was converted into a vector embedding using Sentence Transformers (all-MiniLM-L6-v2), which captures the meaning of the text as numbers
2. HDBSCAN (density-based clustering) grouped semantically similar violations together — violations that meant the same thing ended up in the same cluster even if worded differently
3. GPT-4o was used to label each cluster with a standardized taxonomy name and validate that the crosswalk made semantic sense
4. The unified data was loaded into a DuckDB star schema for analytical querying

Scale:
- NYC: ~272,000 records
- Chicago: ~42,000 records
- Boston: ~106,000 records
- Total: 420,000+ records across 3 incompatible systems

Architecture:
- Data ingestion from NYC, Chicago, and Boston open data APIs using Python
- Sentence Transformers (all-MiniLM-L6-v2) for converting violation text to semantic vectors
- HDBSCAN for density-based clustering of violation categories by semantic similarity
- GPT-4o (OpenAI API) for taxonomy labeling and crosswalk validation
- DuckDB as the analytical database with a star schema (schema.sql defines fact and dimension tables)
- Precision and recall metrics used to validate the quality of the crosswalk

Tech Stack:
- Python (primary language, data ingestion, pipeline orchestration)
- Sentence Transformers (all-MiniLM-L6-v2) — semantic text embeddings
- HDBSCAN — density-based clustering (no need to specify number of clusters)
- GPT-4o (OpenAI API) — violation taxonomy labeling and crosswalk validation
- DuckDB — analytical database with star schema
- SQL (schema.sql with full DDL for fact and dimension tables)

Team Project Note:
DataBridge was a group project with 4 members. Rithujaa's specific contributions were the NLP and semantic intelligence layer (entity resolution), violation taxonomy design, semantic crosswalk validation, RQ4 evaluation, and the methods writeup.

What This Project Demonstrates:
- Creative problem-solving using NLP to automate what would otherwise be manual work
- Understanding of semantic embeddings and how they can be used for entity resolution
- LLM integration (GPT-4o) for validation and labeling tasks
- Dimensional modeling and star schema design
- Working with large, heterogeneous, real-world datasets at scale

PROJECT 8: SPOTIFY SERVERLESS ETL PIPELINE
GitHub: https://github.com/rithujaa/spotify-etl-pipeline
Stars: 7, Forks: 2 (most starred repo)

What It Does:
A fully serverless ETL pipeline that automatically collects data from the Spotify API, processes it with AWS Lambda, stores it in S3, and loads it into Snowflake using Snowpipe. No servers to manage — everything runs on demand triggered by events.

Architecture (Step by Step):
1. A scheduled AWS Lambda function (extract-code.py) connects to the Spotify API and pulls track data including song name, artist, album, and duration. Saves raw JSON to an S3 raw folder.
2. The arrival of the raw JSON in S3 triggers a second AWS Lambda function (transform-code.py) automatically via an S3 event trigger
3. The transform Lambda reshapes and cleans the data into 3 structured CSV files: songs, albums, and artists. Stores them in an S3 processed folder.
4. Snowpipe continuously monitors the S3 processed folder. When new CSVs are detected, it automatically loads them into the corresponding Snowflake tables (songs, albums, artists) with defined primary and foreign keys.

The entire pipeline from Spotify API to Snowflake runs automatically with zero manual intervention.

Tech Stack:
- Spotify API (data source)
- AWS Lambda (Python) — serverless extract and transform functions
- Amazon S3 — raw and processed data storage, event trigger source
- Snowflake — structured data warehouse with relational tables
- Snowpipe — auto-ingestion from S3 into Snowflake
- Python — Lambda function logic
- SQL (spotify_project.sql) — Snowflake table definitions, stages, and loading configuration

What This Project Demonstrates:
- Serverless architecture design (no EC2, no always-on compute)
- Event-driven pipeline automation using S3 triggers
- API integration (Spotify API)
- Snowflake Snowpipe for automated data ingestion
- End-to-end data engineering from API to structured warehouse
