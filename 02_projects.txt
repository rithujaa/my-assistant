PROJECT 1: AI BUSINESS INTELLIGENCE ASSISTANT
Live App: https://ai-bi-assistant.streamlit.app
GitHub: https://github.com/rithujaa/ai-bi-assistant
Built: July 2026 (built and deployed in one afternoon)

What It Does:
An AI-powered business intelligence assistant that lets anyone upload a CSV, Excel, or PDF file and ask questions about their data in plain English. No SQL or coding knowledge required.

Two AI Architectures:
1. For CSV/Excel: GPT-4o writes real pandas code, executes it against the actual dataset, and returns a precise computed answer. This is code generation and execution, not text search.
2. For PDFs: Uses RAG (Retrieval Augmented Generation). The document is chunked using LangChain's RecursiveCharacterTextSplitter, each chunk is embedded using OpenAI text-embedding-ada-002, stored in ChromaDB, and the most semantically relevant chunks are retrieved to answer each question.

Key Features:
- Automatic interactive chart generation using Plotly (GPT-4o decides what chart type is appropriate)
- Data quality report on upload (missing values, duplicates, constant columns)
- One-click executive summary generation
- Suggested questions generated by GPT-4o based on the uploaded dataset
- Chat history with follow-up question memory
- Self-healing code execution (if GPT-4o uses a missing library, the system automatically asks it to rewrite without that library)
- Export conversation as text file
- Settings toggles for showing/hiding pandas code and raw results
- Sidebar with file upload and how-to-use guide

Tech Stack:
- Python
- GPT-4o (OpenAI API) - for code generation, chart generation, executive summaries, suggested questions
- LangChain - for text splitting and RAG pipeline
- ChromaDB (EphemeralClient) - in-memory vector database for PDF RAG
- OpenAI Embeddings (text-embedding-ada-002) - for converting PDF chunks to vectors
- Pandas - for data manipulation and code execution
- Plotly Express - for chart generation
- Streamlit - for the web interface
- PyPDF - for PDF text extraction
- OpenPyXL - for Excel file reading
- SciPy, NumPy - for scientific computing in executed code
- Python-dotenv - for secure API key management

Technical Architecture Details:
- RAG pipeline: text extraction > chunking (1000 chars, 100 overlap) > embedding > ChromaDB storage > semantic retrieval > GPT-4o answer generation
- Code execution pipeline: dataframe description > GPT-4o writes pandas code > exec() runs it > result explained in plain English
- EphemeralClient ensures no data bleeding between different PDF uploads
- Session state management prevents data from mixing between file uploads

Why Built:
Built to learn RAG, LangChain, vector databases, and what it takes to ship a real AI application end to end. Not to compete with ChatGPT but to demonstrate the ability to build production AI applications.

PROJECT 2: REAL-TIME CDC PIPELINE
GitHub: https://github.com/rithujaa/real-time-data-streaming

What It Does:
A production-grade Change Data Capture (CDC) pipeline that streams data from a source system into Snowflake in real time, tracking every change across three data layers.

Architecture:
- Source system generates events
- Apache NiFi picks up events and streams them to AWS S3
- Snowpipe automatically loads new files from S3 into Snowflake RAW layer
- Snowflake Streams detect changes in the RAW table
- Snowflake Tasks trigger SQL stored procedures to process changes
- SCD1 layer: current state (upsert, no history)
- SCD2 layer: full history (tracks every change with effective dates)

Tech Stack:
- Python (data generation and reconciliation scripts)
- AWS EC2 (hosting NiFi)
- AWS S3 (staging area)
- Apache NiFi (real-time event streaming)
- Snowflake (data warehouse)
- Snowpipe (auto-ingest from S3)
- Snowflake Streams (CDC tracking)
- Snowflake Tasks (automated processing)
- SQL stored procedures (SCD1 upserts, SCD2 history tracking)
- Docker (NiFi containerization)

Key Technical Details:
- SCD1 stored procedure: uses MERGE statement to upsert current state
- SCD2 stored procedure: closes old records and inserts new versions with timestamps
- Python reconciliation scripts validate data completeness and accuracy
- Full pipeline documentation maintained for governance

What Was Learned:
- How CDC actually works in production data warehouses
- Snowflake Streams and Tasks in depth
- SCD1 vs SCD2 dimensional modeling
- Real-time data ingestion patterns

PROJECT 3: E-COMMERCE CLOUD DATA PIPELINE
GitHub: https://github.com/rithujaa/ecom-data-pipeline
Stars: 3

What It Does:
An end-to-end data engineering pipeline for an e-commerce dataset built entirely on Azure Cloud. Automates ingestion, transformation, and storage across Bronze, Silver, and Gold Delta Lake layers.

Architecture (verified from README):
1. Raw CSVs uploaded into ADLS landing-zone-1
2. Azure Data Factory detects new files via storage event trigger, converts CSV to Parquet, stores in landing-zone-2
3. Databricks pipeline automatically launches when new Parquet arrives, runs Bronze > Silver > Gold transformations
4. Gold data stored in Delta format in ADLS
5. Azure Synapse Analytics connects to Gold data for querying and dashboarding
6. ADF moves processed files from to_processed_user_data/ to processed_user_data/ automatically

Datasets Used:
- Users, Sellers, Buyers, Countries (e-commerce domain)
- Final Gold table: comprehensive_user_table combining all domains

Key Technical Details:
- Bronze: ingests Parquet from landing-zone-2, schema/type standardization, stores as Delta
- Silver: cleans, enriches, standardizes Bronze data, applies business logic
- Gold: joins and aggregates across domains into unified analytics-ready table
- Users table uses mode("append") for incremental loading
- Event-based triggers automate both ingestion and Databricks execution
- All layers stored as Delta tables in /mnt/delta/tables/{bronze|silver|gold}/
- SQL present: ecom_sql.sql file in repo

Tech Stack:
- Azure Data Factory (orchestration with event triggers)
- Azure Data Lake Storage Gen2 (landing zones and Delta storage)
- Azure Databricks / Apache Spark (PySpark transformation)
- Delta Lake (Bronze/Silver/Gold layers, Delta format)
- Azure Synapse Analytics (consumption layer)
- PySpark (Python) - primary language
- SQL (ecom_sql.sql)
- Jupyter Notebooks (Bronze Layer.ipynb, Silver Layer.ipynb, Gold Layer.ipynb)

PROJECT 4: CROSS-CITY RESTAURANT INSPECTION PIPELINE (DATABRIDGE)
GitHub: https://github.com/rithujaa/DataBridge

What It Does:
A data integration pipeline that unified restaurant inspection data from three incompatible city datasets (NYC, Chicago, Boston) into a single analytical data warehouse.

The Challenge:
Each city had completely different data formats, field names, and violation categorization systems. The same violation type was named completely differently across cities. Manual mapping would have taken weeks.

Solution:
Used NLP and LLMs to automatically match and standardize violation categories across cities.

Architecture:
- Data ingestion from NYC, Chicago, and Boston open data APIs
- NLP-based entity resolution using Sentence Transformers (all-MiniLM-L6-v2)
- HDBSCAN clustering to group semantically similar violation categories
- GPT-4o for violation taxonomy labeling and crosswalk validation
- DuckDB star schema for the analytical data warehouse
- SQL DDL (schema.sql) defines fact and dimension tables

Scale:
- NYC: ~272,000 records
- Chicago: ~42,000 records
- Boston: ~106,000 records
- Total: 420,000+ records

Tech Stack:
- Python (primary language)
- Sentence Transformers (all-MiniLM-L6-v2) - semantic embeddings
- HDBSCAN - density-based clustering
- GPT-4o (OpenAI API) - taxonomy labeling and crosswalk validation
- DuckDB - analytical database
- SQL - star schema design and queries

Team Project Note:
DataBridge was a group project with 4 members. Rithujaa's specific contributions were:
- NLP and semantic intelligence (entity resolution)
- Violation taxonomy design
- Semantic crosswalk validation
- RQ4 evaluation
- Methods writeup

SQL is present in the project (schema.sql with full DDL). GPT-4o was used for LLM labeling.

PROJECT 11: SPOTIFY ETL PIPELINE
GitHub: https://github.com/rithujaa/spotify-etl-pipeline
Stars: 7, Forks: 2

What It Does:
A serverless ETL pipeline that collects data from the Spotify API, processes it using AWS Lambda, stores it in Amazon S3, and automatically loads it into Snowflake using Snowpipe.

Architecture (verified from README):
1. Extract: Scheduled AWS Lambda function connects to Spotify API and pulls track data (song name, artist, album, duration). Saves raw JSON to S3.
2. Transform: S3 event triggers another Lambda function which cleans and reshapes data into 3 structured CSV files: songs, albums, artists. Stored in processed folder in S3.
3. Load: Snowpipe continuously monitors processed folder in S3. When new CSVs detected, automatically loads into corresponding SQL tables in Snowflake with primary and foreign keys.

Tech Stack:
- Spotify API (data source)
- AWS Lambda (Python) - serverless extract and transform functions
- Amazon S3 - raw and processed data storage
- Snowflake - data warehouse with structured tables
- Snowpipe - auto-ingestion from S3
- Python - Lambda functions and API calls
- SQL - table definitions, stages, and loading logic in Snowflake

Files in Repo:
- extract-code.py (Lambda extract function)
- transform-code.py (Lambda transform function)
- spotify_project.sql (Snowflake setup SQL)

Key Notes:
- This is a complete, well-documented project with 7 stars
- Shows serverless architecture expertise (Lambda + S3 + Snowpipe)
- SQL IS used in this project (Snowflake setup)
